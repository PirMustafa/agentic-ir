\chapter{System Implementation and Evaluation}
\label{ch:implementation}

Chapter~\ref{ch:methodology} argued that a multi-hop information need cannot be
served by a single retrieval round, and set out the four agents that answer it.
This chapter describes how those agents are built, how the system is measured,
and what the measurements show. It closes with an error analysis, because a
system that is right for the wrong reasons is not a result.

\section{System Architecture}
\label{sec:architecture}

The brief names four modules --- a query planner, a tool-invocation manager, a
retrieval engine and a validation component. They map onto the four agents of
Chapter~\ref{ch:methodology} and an orchestrator that sequences them.

The orchestrator is an \emph{explicit} state machine rather than a chain of
function calls. Nine states (\texttt{INIT}, \texttt{PLAN}, \texttt{EXECUTE},
\texttt{AGGREGATE}, \texttt{SYNTHESIZE}, \texttt{VERIFY},
\texttt{REPLAN\_GATE}, \texttt{FINALIZE}, \texttt{DONE}) and fourteen labelled
transitions are enumerated in a table in the source, and the transition
sequence taken by each question is written into its trace. This costs more code
than implicit control flow and buys two things. First, the mechanism is
inspectable: the claim that the system re-plans is checkable against a recorded
path rather than asserted. Second, every exit is named, so a question that
terminates early is attributable to a specific guard rather than disappearing
into a generic failure count.

Only one transition runs backwards. \texttt{REPLAN\_GATE} returns to
\texttt{PLAN} when the Verifier's confidence falls below threshold, carrying a
\texttt{ReplanDirective}. Removing that single edge reduces the system to a
retrieve-then-generate pipeline, which is why the ablation in
\S\ref{sec:ablations} isolates it directly.

\subsection{Guarding against non-termination}

An agent that can send work backwards can loop. Five guards are evaluated in
order at \texttt{REPLAN\_GATE}, and the first to fail names the termination
reason recorded in the trace: the re-plan count must be below
\texttt{max\_replans} (2); the iteration count below \texttt{max\_iterations}
(6); at least three LLM calls must remain; elapsed time must be under 60\% of
the 300\,s wall-clock budget; and the directive must be informative, meaning it
names at least one missing item, failed sub-query or suggestion.

A sixth check applies to the plan that comes back. A local 8B model told that
its previous attempt was insufficient will frequently re-emit the same
decomposition in different words. The system therefore normalises each
sub-query --- lowercased, punctuation and placeholders stripped, stopwords
removed --- and rejects a revision whose sub-queries pair with the previous
plan's at a Jaccard similarity of 0.85 or above. Without this, both permitted
re-plans can be consumed re-running an identical plan, and the feedback loop
becomes pure cost.

\section{Implementation Details}

\subsection{Indexing}

Both corpora are indexed twice. The sparse channel is BM25 over stemmed terms
(\texttt{k1}~$=0.9$, \texttt{b}~$=0.4$); the dense channel is
\texttt{bge-small-en-v1.5} \cite{xiao2023cpack} embeddings in a FAISS
inner-product index over L2-normalised vectors, which makes inner product
equivalent to cosine similarity. Both are exact: at this corpus size an
approximate index would trade recall for a speed advantage the system does not
need.

For 2WikiMultihopQA's 54,957 passages the sparse index builds in 4.1\,s and the
dense index in 97.6\,s (95.8\,s of which is GPU encoding), occupying 103.6\,MB
on disk against HotpotQA's 129.1\,MB. The asymmetry between the two build times
is the reason the encoder is given the GPU here and taken off it later
(\S\ref{sec:inference}).

The knowledge graph is induced from passage text alone. For HotpotQA, 417,881
candidate mentions yield 123,759 retained edges over 64,733 nodes in 49.4\,s,
with 446 hub nodes pruned; for 2WikiMultihopQA, 161,572 candidates give 63,073
edges over 52,959 nodes in 32.9\,s with 172 hubs pruned. 76.8\% and 79.0\% of
edges respectively carry a verb-anchored relation label; the remainder are
recorded as untyped co-mention, which the traversal still uses for
connectivity.

That the graph is built from passage text and never from
2WikiMultihopQA's gold evidence triples is not a stylistic preference. Those
triples are the answer key for the very capability the KG Navigator is being
measured on, and a graph built from them would make every KG-attributed gain an
artefact. The constraint is enforced by a test that fails if the graph builder
opens any file whose name contains \texttt{evidence} or \texttt{triple}.

\subsection{Local inference}
\label{sec:inference}

All generation runs on \texttt{qwen3:8b} at Q4\_K\_M quantisation through
Ollama, on an RTX 5060 laptop GPU with 8\,GB of VRAM. No component of this
project contacts a paid API, and a test enforces that no module outside the
model client imports an HTTP library at all.

Measured throughput is 52 tokens per second with the model warm, and a
schema-constrained planning call averages 3.75\,s. Two properties of the
hardware shape the design more than the throughput figure does.

The first is that the card is effectively full. The model and its 8192-token KV
cache occupy 6,707 of 8,151\,MiB with the desktop's own allocation included,
leaving roughly 1.4\,GiB. The three sentence-transformer encoders --- query
embedding, cross-encoder reranking and NLI --- therefore run on CPU at query
time, where they cost well under a second per question against a 300\,s budget.
The GPU is used for encoders only during offline index construction, with the
language model unloaded. An encoder co-resident with the model produces an
out-of-memory failure partway through an evaluation run, which is the most
expensive failure mode available: hours of work lost with partial results.

The second is that the first call after a model load costs approximately
9.5\,s in CUDA warm-up, evaluating a 19-token prompt. Warm, the same work takes
under two seconds. Latency figures in this chapter are therefore reported from
runs with the model resident. One thing the harness does not do should be
stated because the configuration file suggests otherwise. \texttt{config.yaml}
declares a response cache under \texttt{llm.cache}, and the trace schema
carries a cache-hit counter; no cache is implemented. Nothing reads or writes
the declared file, every call in every run reported here went to the model,
and the counter is constitutively zero. Every latency in this chapter is
consequently an uncached measurement, which is the property a timing figure
needs, but it holds because the feature is absent rather than because it was
disabled.

\subsection{Structured output and its failure mode}

Every agent that calls the model does so with a JSON schema and parses the
result through a five-rung ladder: direct parse; strip reasoning blocks and
code fences; a string-aware balanced-brace scan; trailing-comma repair; and
finally a re-prompt carrying the schema and the malformed output. On a
measurement over eight representative multi-hop questions, all eight parsed on
the first rung with no retries and no reasoning leakage.

Suppressing that reasoning is not cosmetic. \texttt{qwen3} is a hybrid
reasoning model, and with thinking enabled and a 128-token generation cap it
spent the entire budget on a 503-character reasoning block and produced no
answer at all. Thinking does not merely add latency here; it starves the
response. It is disabled three ways: an API flag, a system-prompt directive,
and stripping on the response, with the size of any leaked block recorded so
the report can state how often the suppression fails rather than assume it.

\subsection{Budget enforcement}

Each question carries a budget of 20 LLM calls, 6 iterations and 300\,s.
Budget is checked and never raised as an exception: a request for a call
returns a boolean, and an agent that is refused takes its deterministic
fallback. Exception-driven budget control would make ``ran out of calls''
indistinguishable from ``crashed'' in the trace, and those are different
findings.

Two of the twenty calls are reserved. Non-privileged callers --- the planner,
answer extraction and entity linking --- see the reserve subtracted from their
remaining allowance, while the synthesizer and verifier see the true remainder.
Without this, a planner that decomposes aggressively can consume the whole
budget and leave nothing with which to answer, which appears in the results as
a system failure rather than as the budget policy it actually is.

The worst case is 15 calls against the cap of 20, and typical usage is four to
seven. The headroom is deliberate: the cap is a safety net, not a tuning knob.
Most of the saving comes from work the language model never does. Tool routing
is a seven-rule decision table costing nothing --- in practice a one-rule
table, since the Planner's hint decided every routing in the evaluated runs
(\S\ref{sec:tools}); graph traversal is bidirectional breadth-first search;
answer extraction reaches the model only at the fourth of five rungs, and only
for sub-queries that some later sub-query depends on; and the verifier's
adjudication call is issued only inside a narrow band of uncertainty around
its threshold.

\section{Experimental Setup}

All results use the frozen 250-question stratified samples described in
\S\ref{sec:sampling}, drawn once with seed 42 and materialised to disk with
their SHA-256 recorded, so that re-sampling cannot silently occur between runs.
A disjoint 50-question calibration slice, sharing no question identifier with
the evaluation set, is reserved for tuning the verifier threshold.

Every run writes three artefacts: a JSON Lines trace with one complete record
per question, a \texttt{meta.json} capturing the full configuration, library
versions, GPU identity, model digest and seed, and a flat
\texttt{metrics.csv}. The harness checkpoints by appending and skipping
question identifiers already present, so a run interrupted at question 194
resumes at 194. Given that a full agentic configuration takes hours on this
hardware, that is a correctness property rather than a convenience.

Sorting is deterministic throughout, with an explicit tiebreaker --- ranking by
$(-\text{score}, \text{doc\_id})$ rather than by score alone --- because two
passages with identical scores would otherwise be ordered by dictionary
insertion and change the reported metrics between runs.

The implementation is covered by 248 automated tests. Three enforce properties
that would otherwise fail silently: that no module outside the model client can
reach the network, that no agent reads the gold answer carried on the question
state for tracing, and that the knowledge graph builder never opens a gold
evidence file.

\section{Baselines}
\label{sec:baselines}

Five baselines run from weakest to strongest.

\texttt{bm25\_only} and \texttt{dense\_only} isolate the two retrieval channels.
\texttt{hybrid\_rerank} fuses them with reciprocal rank fusion
\cite{cormack2009reciprocal} and reranks the top 50 with a cross-encoder; it is
the strongest non-agentic system available here and the one the agentic system
must actually beat. It is deliberately not weakened: the margin gate that lets
the agentic retriever skip reranking when the fused top result is already
clearly ahead is switched off in the baseline, so every question receives all
50 cross-encoder passes. That gate is an efficiency feature of the agentic
system, and allowing it to skip work inside the opponent would hand the
comparison a head start.

\texttt{naive\_rag} retrieves once with the same hybrid-and-rerank pipeline and
then makes a single generation call. Because it inherits its retrieval from
\texttt{hybrid\_rerank} rather than reimplementing it, the two agree exactly on
every retrieval metric, and the difference between them is one generation step
and nothing else.

\texttt{self\_ask} is the published multi-hop method \cite{press2023selfask}:
the model is asked whether a follow-up question is needed, retrieval is issued
for it, and the loop repeats before a final answer. It has decomposition but no
verification and no re-planning, which makes the gap between it and the full
agentic system the closest available estimate of what the backward edge is
worth.

\section{Evaluation Metrics}

Three families are reported together.

\textbf{Retrieval quality} is Recall@$\{2,5,10\}$, nDCG@10 and MRR, computed
with \texttt{pytrec\_eval}. That library wraps the same evaluation core as
\texttt{trec\_eval}, which produced the published BEIR figures
\cite{thakur2021beir} this work compares against; a reimplementation would risk
breaking that comparability for no gain. Questions without relevance judgments
are excluded rather than scored as zero.

\textbf{Answer quality} is exact match and token-level F1 under the official
HotpotQA normalisation \cite{yang2018hotpotqa}, together with supporting-fact
EM and F1 as set metrics over $(\textit{title}, \textit{sentence id})$ pairs,
and the joint measures. The official yes/no short-circuit is retained: without
it, token-overlap F1 awards partial credit for answering ``no'' where the gold
answer is ``yes'', which is not partial correctness but a wrong categorical
answer.

\textbf{Agent-specific cost} is LLM calls, calls avoided by deterministic
rules, tool calls, latency, plan depth, re-plan rate and citation grounding.
Reporting these beside quality is what the brief asks for, and it is also the
only honest way to present an agentic system: a method that gains three points
of F1 for twenty times the compute has not obviously won, and a table that
omits the denominator invites the reader to assume it did. Two definitions are
fixed explicitly because they are easy to conflate: re-plan rate is the
\emph{fraction of questions} that triggered at least one re-plan, reported
alongside the mean count, and citation grounding is averaged only over
questions that produced an answer, so that ``cited badly'' is not merged with
``did not answer''.

Differences between systems are assessed with a paired bootstrap over 1,000
resamples. Both systems are scored on the same resampled question set at each
iteration; resampling them independently would inflate the variance of the
difference and hide real effects. With 250 questions a difference of a few
points is frequently indistinguishable from noise, and the intervals are
reported so that the reader can see when that is the case.

\section{Results}
\label{sec:results}

Tables~\ref{tab:main-answer-hotpotqa} and~\ref{tab:main-answer-twowiki}
report answer and supporting-fact quality, Tables~\ref{tab:main-retrieval-hotpotqa}
and~\ref{tab:main-retrieval-twowiki} retrieval quality, and
Tables~\ref{tab:agent-metrics-hotpotqa} and~\ref{tab:agent-metrics-twowiki}
the agent-specific cost columns. Every figure in these tables is generated
directly from the run artefacts by \texttt{tables.py} and inserted verbatim; no
number in this report is typed by hand from a run, so the tables and the
recorded runs cannot drift apart. A configuration that has not been run renders
as \texttt{--} rather than as zero, because a zero would read as a measured
failure rather than an absent experiment; a retrieval-only configuration
renders \texttt{--} in the answer columns for the same reason, since it
attempts no answer and scoring the unattempted answer as 0.000 would assert a
failure that never happened.

The retrieval ladder behaves as Chapter~\ref{ch:methodology} predicts. On
HotpotQA the sparse channel reaches Recall@10 of 0.774 and the dense channel
0.816, while fusing them and reranking reaches 0.876 --- an improvement over
the better single channel of six points, obtained without any language model
involvement. Supporting-fact F1 rises correspondingly from 0.330 to 0.412. The
same ordering holds on 2WikiMultihopQA at uniformly lower absolute values,
which is consistent with its longer comparison chains and its larger proportion
of questions whose evidence is distributed across four passages rather than
two.

Answer quality does not follow that ladder, and the first thing to record about
it is that the agentic system does not win. On HotpotQA \texttt{self\_ask}
reaches an exact match of 0.504 and a token F1 of 0.603, \texttt{naive\_rag}
0.496 and 0.581, and \texttt{agentic\_full} 0.432 and 0.510. On
2WikiMultihopQA the leader is unchanged --- \texttt{self\_ask} at 0.264 and
0.310 against \texttt{agentic\_full} at 0.224 and 0.267 --- though there the
full system sits above \texttt{naive\_rag}'s 0.152 and 0.200 on the point
estimates, which is what Chapter~\ref{ch:introduction} predicts of a single
retrieve-then-generate step on chains of three and four hops; no paired
interval between those two systems is computed, and their deltas against the
common reference overlap, so that ordering is not certified. The direction
against \texttt{self\_ask} is consistent across two datasets and both answer
metrics: on the answer string, decomposition with verification loses to
decomposition without it.

That sentence can be given a significance level, and the level is not the
same on the two datasets. The answer columns of
Tables~\ref{tab:main-answer-hotpotqa} and~\ref{tab:main-answer-twowiki} are
referenced to \texttt{self\_ask}, the strongest baseline that produces an
answer string at all, and the $\Delta$F1 column carries the paired bootstrap
of the per-question difference. On HotpotQA \texttt{agentic\_full} is
significantly worse: $\Delta$F1 is $-0.093$ with a 95\% interval of
$[-0.145, -0.039]$, which excludes zero, and the exact-match column carries
the same marker. On 2WikiMultihopQA the difference is $-0.043$ with an interval
of $[-0.100, +0.014]$, which spans zero, so there the deficit is not
established at 95\% and should be read as a point estimate pointing the same
way. The interval is the paired one, over per-question differences on the
identical 250 questions; the per-system F1 intervals printed beside the point
estimates overlap on both datasets, but overlap of marginal intervals is the
wrong test for paired data and is more conservative than the comparison the
table actually makes. An earlier version of these tables referenced the answer
columns to \texttt{hybrid\_rerank}, which attempts no answer, and credited the
agentic system with an apparently significant improvement that was its own F1
with a plus sign; that reference is gone, and the retrieval-only rows now show
\texttt{--} in the answer columns. One further qualification stands: the two
systems are not answering under the same contract, which is the subject of the
paragraphs below rather than an excuse for this one.

Retrieval shows the same deficit from the other side
(Tables~\ref{tab:main-retrieval-hotpotqa} and~\ref{tab:main-retrieval-twowiki}).
\texttt{agentic\_full} records nDCG@10 of 0.763 $[0.734, 0.791]$ on HotpotQA
against 0.835 for \texttt{hybrid\_rerank} and 0.837 for \texttt{self\_ask},
and 0.723 $[0.697, 0.748]$ on 2WikiMultihopQA against 0.756 and 0.790; both
agentic figures carry the marker for significantly \emph{worse} than the
reference.
This is less a failure of the retrieval agent than a consequence of what it is
asked to rank. The ranking reported for a multi-hop configuration is the
reciprocal-rank fusion of every sub-query's list, and a decomposition
deliberately issues narrow queries whose individual lists are each relevant to
one hop and largely irrelevant to the other. Fusing them dilutes the top of the
combined list, where a single well-formed query reranked by a cross-encoder
concentrates it. The 2WikiMultihopQA rows make the mechanism visible:
\texttt{agentic\_full} and \texttt{hybrid\_rerank} tie exactly on Recall@10 at
0.727 while the agentic nDCG@10 is three points lower. The same documents are
being found; they are being found further down, spread across several lists,
because each was retrieved in answer to a different question. Decomposition
buys evidence coverage and pays for it in fused ranking quality, and a single
aggregate ranking metric cannot represent that trade, having been designed for
systems that issue one query. One defect in the state contract qualifies the
agentic retrieval rows specifically. Sub-query identifiers restart at
\texttt{q1} in every plan revision, and per-sub-query results are keyed by
that identifier, so a re-plan's \texttt{q1} overwrites cycle~0's \texttt{q1}
while any identifier the new plan lacks survives from the earlier cycle. For
the 47.2\% of HotpotQA questions that re-planned, the pool over which these
retrieval metrics are fused is therefore the last cycle's results plus
whatever stale entries the last plan did not overwrite, not the union of
everything the question retrieved. Chapter~\ref{ch:conclusions} states the
defect in full; here it means the agentic retrieval rows are a lower bound on
what the question actually found and an exact description of what the
Synthesizer was shown.

Supporting-fact F1 is the metric on which the trade is favourable, and it is
the one this system is built to win. \texttt{agentic\_full} reaches SP-F1 of
0.481 on HotpotQA against 0.412 for \texttt{hybrid\_rerank}, 0.377 for
\texttt{dense\_only} and 0.330 for \texttt{bm25\_only}, and 0.421 on
2WikiMultihopQA against 0.327, 0.314 and 0.273; both margins over the strongest
retrieval baseline are significant under the paired bootstrap. Supporting-fact
EM moves with it, from 0.016 to 0.088 and from 0.016 to 0.124, though those
absolute values say plainly that recovering the gold evidence set
\emph{exactly} remains rare.

Against the two generative baselines the comparison needs more care than a
single column can carry, and an earlier draft of this report got it wrong.
\texttt{naive\_rag} and \texttt{self\_ask} were previously reported at a
supporting-fact F1 of exactly 0.000 and the zero was described as structural
--- systems that emit no supporting facts at all. That was a scoring defect in
the harness, not a property of the systems: both baselines record an evidence
list on every question, but they cite it by passage identifier where the
adapter keys it by evidence identifier, so no citation ever resolved and the
intersection was empty. With the fallback corrected, the two baselines are
scored on their whole evidence pool and reach the starred SP-F1 figures in the
tables, 0.412 and 0.405 on HotpotQA and 0.327 and 0.318 on 2WikiMultihopQA.
Those figures are printed beside the agentic ones but are not comparable with
them, and the star says so. The agentic system is scored on the sentences it
actually cited, a mean of 1.5 sentences per question on HotpotQA and 1.6 on
2WikiMultihopQA; the baselines are scored on everything they retrieved, a
mean of 6.9 and 8.9. The SP-P and SP-R columns show the two protocols pulling
in opposite directions: on HotpotQA the agentic system's cited set has a
precision of 0.654 and a recall of 0.406, where \texttt{self\_ask}'s pool has
a precision of 0.302 and a recall of 0.696, and on 2WikiMultihopQA the
figures are 0.558 and 0.367 against 0.246 and 0.627. A single F1 over two
protocols that trade precision against recall this differently does not rank
the systems, and the tables place no significance mark between rows of
different protocol. The one supporting-fact column that is scored the same
way for every row is \textit{Pool SP-R}, the recall of the whole evidence
pool, and on it the agentic system leads: 0.793 against 0.706 for
\texttt{hybrid\_rerank} on HotpotQA and 0.684 against 0.622 on
2WikiMultihopQA, both significant. So the agentic system retrieves more of
the gold evidence than any baseline and then cites a small, precise subset of
it; its cited-subset SP-F1 is a property of that citation behaviour as much as
of the retrieval, and is not the number on which to rank it against a
pool-scored baseline.

What survives that correction is narrower than the categorical claim it
replaces, and it is still the claim this system is built to support.
Citation grounding --- the fraction of claims with at least one citation that
resolves to a real evidence sentence --- is 0.960 on HotpotQA and 0.976 on
2WikiMultihopQA for \texttt{agentic\_full} and 0.000 for every baseline,
because no baseline citation resolves to anything
(Tables~\ref{tab:agent-metrics-hotpotqa} and~\ref{tab:agent-metrics-twowiki}).
That difference is categorical. The agentic system's citations name specific
sentences that exist and that mostly are gold; the baselines' citations name
nothing that can be checked. The defensible claim from this grid is therefore
about grounded and auditable answers rather than about accuracy: the system
returns a somewhat worse answer with a precise and machine-checkable account of
itself, and on the harder dataset it also recovers more of the gold evidence
than any retrieval baseline.

The cost columns price that account. \texttt{agentic\_full} spends 4.26 model
calls per question on HotpotQA and 3.80 on 2WikiMultihopQA against 1.24 and
1.46 for \texttt{self\_ask}, issues 14.83 and 16.00 tool calls against 2.41 and
2.86, and the plan it finally selected has a mean depth of 1.71 and 1.90 over
1.80 and 2.26 sub-queries. The \textit{Saved} column counts model calls that
a deterministic rule replaced, and its definition has been tightened since an
earlier draft of this report, which credited the system with 7.10 and 7.19
saved calls per question --- more than it spent --- and drew a conclusion from
that. The earlier count credited the routing table and the alias-based entity
linker on every sub-query, although with the shortcut enabled the model router
is unreachable and with alias linking configured there is no model linker to
skip, so neither ever replaced a call this configuration could have made; and
it omitted the extraction ladder, which does replace a real model call on
every sub-query it resolves deterministically. Under the corrected definition
--- a saved call is one that a configured model path would have issued and a
rule pre-empted --- \texttt{agentic\_full} saves 2.60 calls per question on
HotpotQA and 3.10 on 2WikiMultihopQA, against 4.26 and 3.80 spent, and
Tables~\ref{tab:agent-metrics-hotpotqa} and~\ref{tab:agent-metrics-twowiki}
print the per-rule decomposition so that any other definition can be applied
to the same numbers. The gated verifier adjudication and deterministic
extraction displace a real but minority share of the inference a fully
model-driven version of the same design would spend; the claim that they
displace more than the Planner, Synthesizer and Verifier consume between them
is withdrawn. What remains true is that at 52 tokens per second every call
not made is several seconds of wall clock, and that the count is measured
rather than assumed.

Latency is the column that must be read with the most care, and the tables
print it as a median with the maximum beside it rather than as a mean, for a
reason the HotpotQA row makes plain. On 2WikiMultihopQA \texttt{agentic\_full}
costs a median of 35.4\,s per question against 13.2\,s for \texttt{self\_ask}
and 8.3\,s for \texttt{hybrid\_rerank}: roughly two and three-quarter times the
decomposing baseline and a little over four times the non-agentic one, in
exchange for the attribution gain above. On HotpotQA the median is 28.3\,s,
against 4.5\,s and 4.9\,s, and the maximum is 65744.3\,s --- 18.3 hours,
on question \texttt{5a7af32e55429931da12c99c}, inside a single Synthesizer
call. No arrangement of four model calls consumes that budget; the host was
almost certainly suspended with the call open, and the recorded elapsed time
is the suspension. An earlier draft reported the HotpotQA mean, which was that
one question divided by 250 and described nothing that happens per question;
the median is the figure to quote, and the maximum is printed rather than
trimmed so the outlier stays in view. The measurement also identifies a
defect in the budget itself. The 300\,s wall-clock budget of
\S\ref{sec:architecture} is cooperative: it is tested between DAG nodes and
before a call is issued, never during one, so it cannot pre-empt a blocking
call, and the NLI and reranker invocations carry no timeout at all. One
question therefore ran to roughly 220 times its budget without any guard
firing. Bounding a single tool invocation, rather than only the question, is a
correction this measurement identified and which the present results do not
include; Chapter~\ref{ch:conclusions} lists it as a limitation.

\section{Ablation Study}
\label{sec:ablations}

\input{../results/tables/ablations.tex}

Three ablations attribute the system's behaviour to its parts
(Tables~\ref{tab:ablations-hotpotqa} and~\ref{tab:ablations-twowiki}).
Removing the planner collapses the sub-query graph to the question itself: a
single sub-query is routed, retrieved, synthesised and verified, and the
Verifier can still send it back. That is a one-node agentic system, not the
\texttt{hybrid\_rerank} baseline, and the table's own caption is precise about
what the non-agentic floor requires --- removing planning, synthesis and
verification together. Removing the knowledge graph withdraws bridge-entity
discovery while leaving decomposition intact. Removing the verifier disables
the backward edge, leaving a system that plans and retrieves in multiple steps
but never revisits its own answer; the difference between it and the full
system is the contribution of this project, measured rather than asserted.

The study is complete on HotpotQA and still filling on 2WikiMultihopQA, and
each row's sample size is printed so that no reader has to take that on trust.
All three ablations --- \texttt{agentic\_no\_verifier},
\texttt{agentic\_no\_planner} and \texttt{agentic\_no\_kg} --- have covered all
250 HotpotQA questions, so every delta in Table~\ref{tab:ablations-hotpotqa}
is a paired comparison on the identical question set. On 2WikiMultihopQA
\texttt{agentic\_no\_verifier} was mid-run when these tables were generated,
so it is marked preliminary and every delta, $p$-value and significance mark
against it is withheld, and \texttt{agentic\_no\_planner} and
\texttt{agentic\_no\_kg} render as \texttt{--}. Nothing below is concluded
from a 2WikiMultihopQA ablation row.

The verifier ablation is the measurement this project exists to make, and it
lands the way the architecture predicted. With the backward edge removed and
everything else held fixed, exact match on HotpotQA falls from 0.432 to 0.396
and F1 from 0.510 to 0.474; the paired difference is $\Delta$F1 $= -0.037$
with a 95\% interval of $[-0.065, -0.011]$ and $p = 0.008$, and both answer
columns carry the marker for significantly worse. The loop therefore pays for
itself on this dataset in the only currency the ablation measures: the
questions it sends back come back better often enough to move the aggregate.
The price is printed beside it. The full system spends 4.26 model calls per
question against 2.06 without the verifier, and a median of 28.3\,s against
16.5\,s, so the edge roughly doubles both cost columns for a gain of just under
four F1 points. Read with the error analysis below, which finds the Verifier
far more often too permissive than too strict, the result says the mechanism
works when it fires and fires on a minority of the questions where it should.
It is one dataset; the report's own standard elsewhere is that one dataset
does not settle a direction, and the 2WikiMultihopQA row is the one this
section is waiting for.

\begin{sloppypar}
The planner ablation is the surprise, and it is reported as one rather than
smoothed. \texttt{agentic\_no\_planner} scores \emph{above} the full system on
HotpotQA, at an exact match of 0.456 and F1 of 0.543 against 0.432 and 0.510,
with $\Delta$F1 $= +0.033$ $[-0.017, +0.086]$ and $p = 0.186$; the difference is
not significant, and the honest statement is that decomposition did not
measurably help answer accuracy on this dataset and may have hurt it. It did
so at 1.35 model calls per question and a median of 9.7\,s, about a third of
the full system's calls and wall clock. The agent-metrics table shows why the
row is not the \texttt{hybrid\_rerank} floor: the one-node system still
synthesised and verified, grounded its citations at 0.936, and its Verifier
triggered a re-plan on 18.8\% of questions --- every one of which was
discarded as a near-duplicate of the identity plan already run, so the
executed re-plan rate is 0.000 and the row measures the forward pass alone.
Its supporting-fact F1 of 0.508 is the highest of any complete row. Two readings
are consistent with this and the grid does not separate them. The first is
that HotpotQA's two-hop questions are within reach of one well-formed hybrid
query reranked by a cross-encoder --- Recall@10 of 0.876 for that baseline says
as much --- so the Planner's narrow sub-queries dilute a ranking that was
already good, exactly the mechanism the nDCG@10 rows exposed above. The second
is that the Planner's decompositions are simply worse than no decomposition
for an 8B model that then has to compose an answer across them, which would
put the fault in synthesis rather than in planning. Either way the result is a
finding about the planner and not an embarrassment to hide: the component
that the brief's Table~1 lists first is the one whose contribution this grid
cannot yet show, and 2WikiMultihopQA, whose chains are longer, is where the
question will be decided.
\end{sloppypar}

The graph ablation is the one for which a null result was always plausible,
since Chapter~\ref{ch:methodology} describes the induced graph as a navigation
aid rather than a knowledge base, and a null result is what it returns.
\texttt{agentic\_no\_kg} scores an exact match of 0.404 and F1 of 0.501
against the full system's 0.432 and 0.510, a paired $\Delta$F1 of $-0.009$
with a 95\% interval of $[-0.048, +0.029]$ and $p = 0.646$. The interval sits
a whisker below zero and spans it comfortably, so on this dataset the
knowledge graph cannot be shown to help answer accuracy at all.

The retrieval table makes the point more sharply, because it measures the
component on its own terms. Without the graph, Recall@10 is 0.820 against the
full system's 0.812 and nDCG@10 is 0.766 $[0.737, 0.793]$ against 0.763
$[0.734, 0.791]$ --- intervals that all but coincide --- and the failure
profile records 15 bridge-link failures rather than 17. Bridge-entity
discovery is exactly what the graph was added to supply, so the null appears
first in the metric the component was chosen for and not only in the aggregate
downstream of it. What the graph does change is the bill. Tool calls fall from
14.83 per question to 8.15 and median latency from 28.3\,s to 11.8\,s, while
model calls are unchanged at 4.28 against 4.26: almost half of the full
system's tool calls are graph lookups, and on HotpotQA they buy nothing this
grid can measure.

Two readings survive and the grid does not separate them. The first is that
HotpotQA's two-hop questions rarely need a bridge the retriever has not
already surfaced --- the same explanation the planner ablation invited, and
consistent with \texttt{hybrid\_rerank}'s Recall@10 of 0.876 --- so the
graph's value, if it has one, must be looked for on longer chains. That is the
2WikiMultihopQA row, and it is the second thing this section is waiting for.
The second reading is that the induced graph is too sparse for its
neighbourhoods to add anything, which would make the null a fact about this
graph rather than about graph navigation as a technique.
Chapter~\ref{ch:conclusions} keeps both open and states what would decide
between them.

\section{Error Analysis}
\label{sec:errors}

\input{../results/tables/error_analysis.tex}

Failures are categorised automatically from the traces against the gold
supporting facts, first match winning: parse failure, budget exhaustion,
retrieval miss, decomposition error, bridge-link failure, synthesis error,
verifier false accept, and verifier false reject. The last of these --- a
discarded cycle whose answer was correct while the selected one is not --- is
what makes the backward edge falsifiable, and it is reported whatever it shows.

The taxonomy accounts for nearly all of what went wrong, as
Tables~\ref{tab:error-analysis-hotpotqa} and~\ref{tab:error-analysis-twowiki}
show. Of \texttt{agentic\_full}'s 142 HotpotQA errors and 194 on
2WikiMultihopQA, only
16 and 23 fall through the cascade with no rule firing, so the profile is a
description of the failures rather than a partition of a residue. Neither
dataset records a single parse failure or budget exhaustion in any
configuration, which retires two concerns the design spent effort on: the
five-rung parse ladder and the reserved-call policy are doing their work, and
nothing in these results is an artefact of malformed model output or of a
question that ran out of allowance. The counterweight column is the important
one for the central claim. Two questions on HotpotQA and five on
2WikiMultihopQA were \emph{recoverable} --- some cycle produced a correct answer
that was not the one finally selected --- and those same counts are the false
rejects. The backward edge is therefore not discarding good answers at any
material rate; its problem, as \S\ref{sec:discussion} develops, is the opposite
one.

\begin{sloppypar}
One record in the HotpotQA trace shows the shape of that opposite problem
better than the aggregate does, and it is the same question that produced the
18-hour latency above, \texttt{5a7af32e55429931da12c99c}. The system answered
\emph{New York City} where the gold answer is \emph{Brooklyn, New York}, and the
answer sentence it emitted alongside was copied from an evidence sentence
unrelated to the question. The trace record scores that sentence at an NLI
support above 0.99 and a citation grounding of 1.0 --- the sentence is, after
all, entailed by the evidence it was copied from --- against a retrieval
agreement of 0.0, and the Verifier accepted the answer at a confidence of
0.82; Chapter~
ef{ch:conclusions} quotes the exact component values from
the record. Nothing in the blend is miscomputed. The Verifier entails the \texttt{answer\_sentence} field and never
the \texttt{answer} itself, so an answer sentence that is faithful to a cited
sentence but not to the question passes at high confidence regardless of what
the answer string says. This is a property of the design rather than of the
run, it is the single most instructive failure in the grid, and
Chapter~\ref{ch:conclusions} carries it as a limitation.
\end{sloppypar}

One failure mode found during development deserves recording, because it is a
property of agentic systems generally and not of this implementation. The
verifier's confidence blend weights entailment at 0.45. When the NLI encoder
was unavailable, the verifier fell back as designed to token containment, which
scored 1.000 support on an answer where the entailment model scores 0.0008 ---
correctly refusing to entail a comparison from one operand's date alone. The
fallback is safe in that it never raises; it is not safe for the results.
Because entailment dominates the blend, a silent fallback pushes nearly every
answer above the acceptance threshold, the verdict becomes uniformly
\emph{accept}, and the backward edge never fires. The run completes, the
numbers look plausible, and the central measurement of the project quietly
becomes an artefact.

Nothing in the output distinguishes that run from a healthy one except a
degradation flag in the trace. The system now performs an explicit preflight
check that loads the encoder and verifies a self-entailment before an
evaluation begins, and refuses to start otherwise. The general lesson is that a
graceful degradation path in an agentic system is a measurement hazard: it
converts a loud failure into a quiet bias, and the component most worth
protecting is the one carrying the most weight in a decision.

\section{Discussion}
\label{sec:discussion}

The grid does not support the claim this project would have preferred to make.
Agency did not buy accuracy. On both datasets a published decomposition method
with no verification and no feedback edge answers more questions correctly than
the four-agent system, at roughly a third of the model calls and a fraction of
the wall clock, and the fused ranking the agentic system produces is
significantly worse than a single hybrid query reranked by a cross-encoder. Any
reading of these tables that concludes otherwise is reading them wrongly.

Agency did buy something else, and the failure profile shows what. Against
\texttt{hybrid\_rerank}, \texttt{agentic\_full} reduces the share of questions
labelled \texttt{decomposition\_error} from 0.248 to 0.064 on HotpotQA and from
0.552 to 0.088 on 2WikiMultihopQA, and \texttt{bridge\_link\_failure} from
0.552 to 0.068 and from 0.200 to 0.028. Those are the two failure classes that
Chapter~\ref{ch:introduction} argued a single-shot ranker cannot address in
principle, and they have very largely gone. What has replaced them is
\texttt{synthesis\_error}, at 0.228 and 0.236 --- by a wide margin the dominant
agentic failure mode, and more than three times the corresponding rate for
\texttt{self\_ask}, which is 0.064 and 0.076. The diagnosis this licenses is
precise and it reconciles
every result above. The system now finds the right evidence and then composes
the wrong string from it. That is exactly the profile of a system with high
supporting-fact F1 and low exact match, and it says that the marginal
engineering effort belongs in extraction and synthesis rather than in more
planning, more traversal, or more retrieval.

The verifier's behaviour is the second half of the same picture. The traces
record 92 false accepts on HotpotQA and 154 on 2WikiMultihopQA --- answers the
Verifier passed that the gold supporting facts do not support --- against 2 and
5 false rejects. The loop is therefore not too strict but far too permissive,
and the threshold calibration reported in Chapter~\ref{ch:conclusions} explains why
it cannot easily be made stricter: the confidence blend separates correct from
incorrect answers only weakly, so moving the threshold trades false accepts for
false rejects along a shallow curve rather than cleanly removing them. That
places the ceiling on this design where the error profile already put it. A
verifier that scores an answer sentence against its citations can detect that
an answer is unsupported; it has no mechanism for detecting that a
\emph{well-supported} answer is the wrong span of a correct sentence, which is
what a synthesis error usually is.

A practitioner reading this should take the following. If the deliverable is a
ranked list of passages, use \texttt{hybrid\_rerank}: it is the best ranker
here, costs no model calls, and nothing in this report displaces it. If the
deliverable is a short answer string and cost matters, use \texttt{self\_ask};
it is the accuracy leader on both benchmarks at 1.24 and 1.46 model calls per
question. The four-agent system earns its cost only where the answer must be
attributable --- where a reader has to be able to check which sentences support
the claim, and where an unsupported answer is worse than a slow one. On that
axis the difference is categorical in one respect and only in that one: the
agentic system's citations resolve to real sentences at a grounding of 0.960
and 0.976, and no baseline's citations resolve at all. Its supporting-fact F1
is a property of a precise cited subset, and the pool-scored figures for
\texttt{self\_ask} and \texttt{naive\_rag} are not the same measurement, so no
ranking on that column is claimed. Whether an auditable answer is worth close
to three times the median latency of the decomposing baseline is a property of
the deployment and not of the benchmark, and the tables are reported in a form
that lets the reader decide it rather than being told.

Two further observations hold independently of the ablation grid.

The first concerns where intelligence is worth spending, and what the run
showed is not quite what was designed. The retrieval agent was built to route
every sub-query through a seven-rule decision table and issue no model calls;
it issued none, but the trace shows that the first rule --- honour the
Planner's tool hint --- fired on every one of the routing decisions in the
headline HotpotQA run, because the Planner attached a hint to every sub-query
it emitted, and the six lexical rules behind it never executed. The routing
decision was therefore made by the model after all, inside the planning call
the system pays for anyway, and the table's contribution was to avoid asking
twice. That is still a saving, and the graph navigator remains fully
deterministic; but the finding is about the division of labour between agents
rather than about rules replacing a model. It also closes off the experiment
\S\ref{sec:tools} designed to test the rules against a model router: with a
hint on every sub-query the model router is unreachable as the code stands,
and no agreement rate is reported. The open question this leaves is whether
the Planner's hints agree with what the lexical rules would have chosen, which
the trace can answer offline and this report does not.

The second concerns self-report. The planner produces structurally correct
decompositions --- correct bridge shape, correct dependency placeholders --- and
then labels its own strategy wrongly on seven of eight questions, calling
obvious bridge and comparison plans \texttt{single\_hop}. The system therefore
derives the strategy from the shape of the dependency graph and retains the
model's own label only for comparison. That an 8B model can build a correct
structure and misname it is a specific, checkable claim about where such models
can be trusted, and it generalises beyond this system: an agentic architecture
that routes on a model's self-assessment is resting on a weaker signal than one
that routes on what the model actually produced.
